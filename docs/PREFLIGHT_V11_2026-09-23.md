### What the runner cap enforces, and what it cannot

`--max-usd` is compared in the preflight with the largest modelled scenario
(now USD 0.365 for v11). A cap below it refuses the run before any request. A
cap of USD 0.30 would therefore be refused; the earlier proposal of 0.30 was
wrong. After the run the cap is compared with the cost computed from the
returned usage block and the report says "within cap: no" if exceeded.

The cap does not stop a running workflow. One POST starts the hosted run and
the service executes every node server side; the runner only streams and
polls. The 1,500 second deadline stops the runner's polling, not the run. The
runner never retries: a 429 or any failure raises and the run stops with the
response id recorded for read-back. No Azure hard spending limit exists on
this subscription (pay as you go, spending limit off, no budget configured).
The only hard bound on cost is structural: at most fifteen agent invocations
per run, one run per command, one command per approval.

### Does publishing agent v7 change the v10 binding

Yes. The workflow YAML names each agent (`agent: name: EvidenceComplianceAgent`)
without a version, and the endpoint selector resolves "@latest". Once v7 is
published, any run of workflow v10 would also invoke compliance v7. No further
v10 run is planned, and the three v10 evidence folders are frozen files that
no publish can alter, so this is acceptable, but it must be stated: after step
0a there is no live configuration that reproduces the final run of 2026-09-20
exactly. Whether the selector can pin a fixed version instead of "@latest" has
not been tested and is not relied on.

### How v11 is selected and executed

The runner sends `agent_reference: {name: GridResolveAIWorkflow}`, so the
hosted service runs whatever version is latest. Selection is therefore by
publish order plus verification:

1. Publish v11. It becomes latest.
2. Set `GRIDRESOLVE_WORKFLOW_VERSION=11` for the runner. Its live check reads
   the workflow and refuses to run unless latest version is exactly 11, not a
   draft, and the agent state is enabled. It also refuses a case input whose
   `workflow_version` label is not "GridResolveAIWorkflow v11".
3. The run's action ids are interpreted with runner/workflow_v11.py; any id
   outside that map is reported, never guessed.

### Preservation

The three folders under evidence/runtime/ are read by every test and written
by none; tests/test_workflow_engine_v11.py asserts the final run's files are
unmodified after every scenario, and tests/test_evaluation_v2_1.py asserts
dataset D and the v2.0 packs are byte-identical to git HEAD. Each new run
writes its own folder `evidence/runtime/<utc stamp>_<case>_<8 hex>/` and
claims a slot in the run ledger; SYN-CASE-4003 has three prior attempts, so
its run needs `--allow-additional-run`; 4001 and 4007 have none.

### Rollback

Agent and workflow versions are immutable and retained; publishing never
edits an earlier version. Rollback means publishing the earlier definition
again as a newer version, then reading it back:

```
python scripts/publish_agent_version.py --agent EvidenceComplianceAgent --file agents/EvidenceComplianceAgent.v6.md --description "rollback to v6 text" --confirm PUBLISH
python scripts/publish_agent_version.py --workflow GridResolveAIWorkflow --yaml tests/workflow_engine/workflows/GridResolveAIWorkflow_v10.yaml --description "rollback to v10 definition" --confirm PUBLISH
python tests/verify_live_config.py
```

After a rollback the workflow's latest version number is higher than 10 even
though its definition is v10, so the runner would need
`GRIDRESOLVE_WORKFLOW_VERSION` extended to that number before any further v10
run; runner/workflow_versions.py maps unknown numbers to nothing on purpose.
Whether a version can be deleted through the control plane is unverified and
not part of the plan.

## 3. v11 safety preflight

Each line names the local check that establishes it. The engine is Microsoft's
open-source declarative runtime running the same YAML; it is calibrated
against the v6 defect and the v10 final run, but it is not the hosted service.

| Property | Where it is enforced | Local check, all PASS in tests/test_workflow_engine_v11.py (76 of 76) |
| --- | --- | --- |
| Release needs the decision object, the approval token, a complete investigation and six readable fields | attempt-0 approve condition is v10's expression (token exactly once, exactly the last line, no ESCALATE substring, six non-blank fields, evidence, usage, policy and compliance outputs each start with `{` and hold their key) plus `!("GRIDRESOLVE_REJECT" in t)`; every later gate repeats it on its own attempt's variables | "the attempt-0 approve expression is v10's, plus the REJECT exclusion"; "a corrected draft with a blank field is withheld and escalated"; "a corrected draft that is not JSON is withheld and escalated" |
| Malformed compliance output fails closed | the gate's last branch is `condition: "true"` into the escalation node | "a malformed token at attempt 1: nothing sent, escalated once, audited"; "prose only at attempt 1"; "an empty output at attempt 1"; "approved token present but the decision rejects and the text holds a REJECT token: not released, not corrected, escalated"; "the rewrite token alone, no decision object: no correction is attempted, escalated" |
| Reason codes on every non-approval | the workflow does not read reason codes by design; the v7 instructions make `reason_codes` mandatory on every decision other than APPROVE, and the offline check `escalation_reason_codes` FAILS any escalated run without them. A hosted run that escalates without codes fails criterion 6 and 13 of the acceptance plan and is reported as such | "reason codes present or absent, the route is the same: they are for people and checks"; tests/test_escalation_reason_codes.py, 20 of 20 |
| An escalation cannot send the rejected draft | the only SendActivity nodes sit inside approve branches, each sending its own attempt's draft variable; the escalation branch holds no SendActivity | "the rejected draft was not sent"; "each correction attempt reviews a fresh draft variable, never the rejected one"; "on every path at most one message reaches the customer"; "no SendActivity activity is written as an =expression" |
| Message approval and case follow-up stay separate | the follow-up gate reads the planner's final line, never the compliance output, and runs only inside an approve branch | "the new plan cleared the case, so no human handoff was created"; "and the reverse: the original plan cleared the case but the new plan does not, so a handoff is created" |
| Retries cannot bypass the two-attempt limit | the tree is unrolled to depth two; after the second correction a gate offers only release or fail closed, so a third rejection token has no branch to take | "the tree is unrolled to exactly two correction attempts"; "after the second correction a gate can only release or fail closed"; "rewrite, rewrite, then a third rewrite request, which the shape cannot grant: two corrections, then escalation"; "replan, replan, then a third replan request"; "three scripted approvals: one release" |
| Audit last, once, on every path | audit node after the outer condition group | "on every path the terminal audit runs last and exactly once" |

Not covered locally: the hosted service's own retry or timeout behaviour
inside a node, and whether it evaluates Power Fx identically to the open-source
engine for the new REJECT exclusion. Both are findings a hosted run can
produce.

### Runner safety controls

Exact confirmation phrase required; explicit cap required and refused below
the modelled worst case; synthetic-only validator and leak-marker refusal on
the payload; case label must name the targeted version; read-only live check
of version, draft state and agent state before the billable POST; one POST,
no retry, 429 stops the run; run ledger slot claimed before and closed after,
a second attempt on the same case needs `--allow-additional-run`; every
action id interpreted against the v11 map, unknown ids reported; cost from
the usage block with the price source printed, "unmeasured" if absent.

### Rollback

### Stop conditions

A publish read-back that does not match the local file. A live check that
fails. Any HTTP 429 or transport failure (the run is not retried; the response
id is read back instead). A usage block missing (cost reported as unmeasured,
no further run until explained). A run cost above the cap. A billing line for
anything other than Foundry Models or log ingestion. Any workflow action id
outside the v11 map. Any message authored by the workflow in a run that was
expected to escalate. Any of these stops the batch before the next command.

Approval is requested for steps 0a, 0b, 0c and run 1 first. Runs 2 and 3
each wait for a separate go after run 1 is scored.
